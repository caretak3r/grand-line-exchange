  fix, and the README corrections must land together — a migrated file without
  the scraper change regresses on the next bot run, and a scraper change
  without the migration breaks sale-row dedup between old and new labels.

## Findings considered and rejected

Recorded so nobody re-audits these:

- **Hourly git commits/deploys and git-as-database**: fine as-is. After 1,226
  commits the repo packs to 2.66 MiB — git delta-compresses the JSON well, and
  public repos get unlimited Actions minutes. Do not re-architect persistence
  or deployment.
- **Dual-runtime analytics per se** (Python owns ingest-time values, JS owns
  display derivations): acceptable for a single-consumer hobby app. The fix is
  the documented ownership rule + module extraction (plan 005), not a
  cross-runtime canonical analytics layer.
- **Splitting Dashboard.jsx's JSX into components**: cosmetic; deferred unless
  the file keeps growing.
- **Relabeling MAs to "7-obs MA" instead of fixing them** (alternative to plan
  004): rejected — honest labels would still leave RSI computed over a series
  where one liquid set's afternoon weighs as much as another set's month.
- **Having Python shell out to `node -e` to read sets.js** (alternative to
  plan 001): rejected — adds a Node dependency to a deliberately stdlib-only
  scraper.
- **Per-set sharded JSON files with a manifest** (alternative to plan 002's
  retention): rejected — 22 extra fetches/files for a payload that gzips to
  roughly 150 KB on Pages.
- **Moving history out of the repo** (Releases, separate branch, external
  store): rejected — breaks the "repo is the database" simplicity that is the
  project's core design (`README.md:88`).
